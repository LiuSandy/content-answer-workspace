# Feature: Chat 采集结果任务消息渲染

## 背景（Background）

当前 Chat 模块在 AI 调用平台采集工具后，会把一次任务拆成多条消息渲染：工具过程消息、采集结果卡片、最终 AI 回答气泡。实际效果中，采集结果卡片以整行大面板出现，而最终回答仍是普通窄气泡，导致同一次 AI 回答在视觉上被割裂，且工具结果比 AI 总结更像主内容。

用户在 Chat 中发起类似“在知乎平台采集一些关于个人网站搭建的问题”时，核心诉求不是查看原始工具日志，而是获得一条完整的 AI 任务结果：先读 AI 对采集结果的总结，再在同一条消息内对平台采集结果进行选择、打开链接和导入工作台。

当前 Chat 对话流式接口仍使用旧式 `fetch + ReadableStream` 解析 SSE：业务事件只放在 `data.type` 中，没有标准 SSE `id` 和 `event` 字段，也没有基于 `Last-Event-ID` 的断点补发。用户在 AI 调用工具或输出长回答时，如果页面刷新、网络短断或连接中断，前端无法可靠恢复当前对话运行。

本功能用于重新规划 Chat 中平台采集结果的渲染方式，并把 Chat 对话流式接口升级为可靠 SSE 对话运行模型，使 AI 回答、平台采集结果和导入操作成为一条统一、可读、可操作且可恢复的任务结果消息。

## 目标（Goal）

将平台采集工具返回的结构化条目，在 Chat 列表中渲染为同一条 assistant 任务结果消息的内嵌结果区。该消息先展示 AI 总结回答，再展示轻量的采集结果操作区，支持用户勾选结果、打开原链接、展开全部结果并导入工作台。

同时，将 Chat 对话发送升级为“创建对话运行 + EventSource 订阅”的可靠 SSE 流程。服务端为同一次对话运行的业务事件分配递增 id、缓存事件，并支持重连或刷新后按 `Last-Event-ID` 或 `lastEventId` 查询参数补发缺失事件。

## 非目标（Non-Goals）

- 不修改平台采集工具本身的采集逻辑。
- 不对回答引用来源、分析类结构化结果、普通工具日志做专门格式化。
- 不在 Chat 消息内展示搜索框。
- 不在 Chat 消息内展示平台筛选控件。
- 不在 Chat 消息内展示分组筛选控件。
- 不把 Chat 中的采集结果区做成完整工作台页面。
- 不改变工作台已有的回答生成、编辑和保存流程。
- 不修改 `feature-reliable-sse-generation.md` 中工作台单条回答生成 job 的既有语义。
- 不迁移回答精修、热榜分析、批量生成、润色等其它旧流式接口。
- 不要求跨进程、跨服务重启恢复 Chat 对话运行；第一阶段只要求单进程内存事件缓存结合既有 LangGraph 会话持久化。
- 不在本 spec 阶段编写实现代码。

## 用户故事（User Stories）

- 作为内容运营用户，我希望在 Chat 中让 AI 采集知乎、小红书等平台内容后，看到一条完整的任务结果消息，以便快速理解 AI 做了什么并继续操作结果。
- 作为内容运营用户，我希望先看到 AI 对采集结果的总结，再看到可操作的结果列表，以便先判断采集质量，再决定导入哪些条目。
- 作为内容运营用户，我希望在采集结果区勾选条目并导入工作台，以便后续批量生成回答。
- 作为内容运营用户，我希望每条采集结果可以打开原链接，以便在导入前核验来源。
- 作为内容运营用户，我希望结果默认只展示少量条目，并能展开查看全部，以便 Chat 列表不被大量结果撑得过长。
- 作为内容运营用户，我希望 Chat 中 AI 正在调用工具或输出长回答时，网络短暂中断后可以继续接收缺失内容，以便不中断当前对话任务。
- 作为内容运营用户，我希望生成过程中刷新页面后能恢复当前对话运行或看到已完成结果，以便误操作不会丢失已经开始的采集和回答。

## 功能需求（Requirements）

1. Chat 中一次平台采集任务完成后，应渲染为一条统一的 assistant 任务结果消息，而不是独立渲染为“工具过程消息 + 采集结果卡片 + AI 回答气泡”三块割裂内容。
2. 任务结果消息顶部应显示任务摘要信息，至少包含任务完成状态、采集主题或关键词、平台名称和结果数量。
3. 任务结果消息应先显示 AI 最终总结回答，AI 总结继续使用通用 Markdown 渲染。
4. 任务结果消息应在 AI 总结下方显示平台采集结果操作区。
5. 只有平台采集工具返回的条目列表进入专用结果操作区；非平台采集结果继续按通用 Chat 渲染规则处理。
6. 结果操作区应显示结果总数和已选数量。
7. 结果操作区应支持单条勾选和取消勾选。
8. 结果操作区应支持全选和取消全选。
9. 结果操作区应支持导入已选条目到工作台。
10. 结果操作区应支持每条结果打开原链接。
11. 结果操作区应默认只展示前若干条结果，避免大量条目撑爆 Chat 列表。
12. 当结果数量超过默认展示数量时，结果操作区应提供“展开查看全部”和“收起”能力。
13. 结果操作区可展示分组统计标签，例如“新手入门 28”“SEO 引流 24”；这些标签只用于统计展示，不提供点击筛选行为。
14. 如果采集结果没有可用分组字段或分组统计，结果操作区不应显示空的分组标签区域。
15. 结果操作区不得显示搜索框。
16. 结果操作区不得显示平台筛选控件。
17. 结果操作区不得显示分组筛选控件。
18. 导入成功后，应给出明确反馈，说明新增条目数和跳过重复条目数。
19. 导入结果应复用现有工作台去重逻辑，避免同一 URL 或同一结果重复导入。
20. 结果区应在移动宽度下保持可读，不允许标题、按钮、统计文字互相重叠。
21. Chat 发送消息应升级为两阶段流程：先创建对话运行，再使用 `EventSource` 订阅该运行的 SSE 事件。
22. 创建对话运行接口必须接收 `sessionId` 和用户消息，返回 `runId` 与运行状态，并立即返回；实际对话执行在后台继续。
23. 对话运行的后台执行不得依赖当前 SSE 连接；SSE 连接断开不得取消后台工具调用或 AI 输出。
24. 每个对话运行必须有状态：`pending`、`running`、`done`、`error`、`canceled`。已清理运行通过“运行不存在或已过期”的错误语义表达。
25. 每个对话运行内的可恢复业务事件必须带递增整数 `id`，同一个运行内不得重复或倒退。
26. Chat SSE 订阅接口必须使用标准 SSE 字段输出：`id`、`event`、`data`。
27. Chat SSE 业务事件至少包括：`tool_start`、`tool_end`、`collect_result`、`chunk`、`done`、`chat_error`、`canceled`。
28. Chat SSE 可发送 `heartbeat` 保活事件；`heartbeat` 不参与恢复缓存，不占用递增业务 id。
29. 运行失败后必须发送 `chat_error` 事件，不得使用业务 `event: error`，避免与 `EventSource.onerror` 网络错误语义混淆。
30. 服务端必须缓存对话运行事件和最终结果。第一阶段使用单进程内存缓存，终态运行至少保留 30 分钟。
31. 服务端必须支持通过 `Last-Event-ID` 请求头补发所有 `id > Last-Event-ID` 的缓存业务事件。
32. 页面刷新后新建 `EventSource` 时，前端必须带上本地保存的 `lastEventId` 查询参数；服务端必须支持 `?lastEventId=<number>`，其优先级低于 `Last-Event-ID` 请求头。
33. 订阅已完成运行时，服务端必须补发指定 id 之后到 `done` 的事件，然后关闭连接。
34. 订阅运行中对话时，服务端必须先补发缺失事件，再继续推送新事件。
35. 订阅不存在或已过期的运行时，服务端必须返回明确错误，前端提示“对话运行不存在或已过期，请重新发送”。
36. 前端必须记录当前运行的 `runId`、`sessionId`、`lastEventId`、流式文本、工具步骤和采集结果到同一浏览器会话可恢复的位置，例如 `sessionStorage`。
37. 页面刷新后，如果本地存在未完成的 Chat 运行记录，前端必须查询运行状态并恢复订阅；如果运行已完成，前端必须直接展示最终消息结构。
38. 前端收到重复事件或乱序事件时，必须按事件 id 去重；`id <= lastEventId` 的业务事件不得重复应用。
39. `EventSource.onerror` 只表示连接异常或浏览器准备重连，不得立即把对话运行标记为失败。只有收到 `chat_error`、`canceled`、明确的运行查询错误，或超过约定恢复超时仍无进展时，才进入错误或中断状态。
40. 旧的 Chat 流式接口如保留，必须与新可靠 SSE 接口并存；新 Chat 页面默认使用可靠 SSE 对话运行接口。

## 验收标准（Acceptance Criteria）

1. 正常路径：当 AI 调用平台采集工具并返回 1 条以上结果时，Chat 列表中出现一条统一的 assistant 任务结果消息，消息内先显示 AI 总结，再显示采集结果操作区。
2. 正常路径：采集结果区显示平台、主题或关键词、结果总数和已选数量。
3. 正常路径：用户可以勾选单条结果，已选数量随之更新。
4. 正常路径：用户可以点击全选，全部当前结果进入选中状态；再次点击可取消全选。
5. 正常路径：用户点击“导入已选”后，选中结果进入工作台，并显示导入成功反馈。
6. 正常路径：用户点击单条结果的“打开”操作后，在新窗口或新标签页打开该结果原链接。
7. 正常路径：当结果数超过默认展示数量时，默认只展示前若干条，并显示“展开查看全部”；点击后展示全部，再点击“收起”恢复默认展示。
8. 正常路径：如果存在分组统计，分组标签只显示名称和数量；点击标签不会改变列表内容。
9. 错误路径：当导入结果全部为重复条目时，工作台不新增条目，并显示“已跳过重复”之类的反馈。
10. 错误路径：当用户未选择任何条目且点击导入时，界面应有明确行为：要么导入全部结果，要么禁用导入按钮；具体行为需在 plan 阶段固定，不能出现无反馈。
11. 错误路径：当某条结果缺少 URL 时，该条不显示打开原链接操作，导入时仍可按可用字段进入工作台或被明确跳过。
12. 边界情况：当平台采集工具返回 0 条结果时，不显示空列表操作区，AI 总结中说明未采集到可用结果。
13. 边界情况：当结果标题很长时，标题应换行或截断，不得挤压勾选框、打开按钮或导入按钮。
14. 边界情况：在移动宽度下，结果区操作按钮应换行或收敛，不能与统计信息重叠。
15. 回归标准：Chat 中普通 assistant 文本消息仍按现有 Markdown 气泡渲染。
16. 回归标准：非平台采集工具结果不进入采集结果操作区。
17. 回归标准：结果操作区中不存在搜索框、平台筛选控件和分组筛选控件。
18. 正常路径：用户发送 Chat 消息后，前端先收到 `runId`，随后通过 `EventSource` 收到标准 SSE 事件。
19. 正常路径：`tool_start`、`tool_end`、`collect_result`、`chunk`、`done`、`chat_error`、`canceled` 业务事件都有递增 id；`heartbeat` 不改变 `lastEventId`。
20. 正常路径：AI 文本通过 `chunk` 事件持续追加显示，收到 `done` 后最终消息内容等于 `done.reply`。
21. 正常路径：平台采集结果通过 `collect_result` 事件进入当前运行的采集结果集合，最终与 `done.reply` 合并为同一条 assistant 任务结果消息。
22. 正常路径：断网后浏览器自动重连时，服务端根据 `Last-Event-ID` 补发缺失事件，前端文本和采集结果不重复、不缺失。
23. 正常路径：生成过程中刷新页面后，前端用本地保存的 `runId` 和 `lastEventId` 恢复订阅；如果运行已完成，页面直接显示完整任务结果消息。
24. 错误路径：服务端发送 `chat_error` 后，前端显示错误信息，不把部分流式内容提交为最终 assistant 消息。
25. 错误路径：订阅不存在或已过期的运行时，前端清理本地运行记录并提示用户可重新发送。
26. 边界情况：前端收到重复事件时忽略该事件，不重复追加文本、不重复加入采集结果。
27. 边界情况：运行被取消时，前端关闭订阅并显示取消状态，不继续更新该运行的 UI。

## 边界情况（Edge Cases）

- 平台采集工具返回空 `items`。
- 平台采集工具返回的条目缺少 `url`。
- 平台采集工具返回的条目缺少 `excerpt`、`metric` 或 `author`。
- 多个平台采集工具在同一轮对话中返回多个结果集合。
- 同一平台结果数量很大，例如 90 条以上。
- 用户展开全部后再导入部分条目。
- 用户导入已存在于工作台的重复条目。
- AI 最终回答为空，但采集结果存在。
- 流式过程中采集结果先返回，最终回答后返回。
- 用户刷新页面后查看历史消息，任务结果消息仍应保持同样结构。
- Chat 对话运行中网络短断，浏览器自动重连。
- Chat 对话运行中页面刷新，本地存在 `runId` 和 `lastEventId`。
- Chat 对话运行已完成后再次订阅。
- Chat 对话运行已过期或服务端重启后本地仍有旧 `runId`。
- 前端收到重复事件、乱序事件或跳号事件。
- `EventSource.onerror` 触发但服务端后台运行仍在继续。
- 服务端发送 `chat_error` 或 `canceled` 终态事件。

## 交互与界面行为（UX / UI Behavior）

任务结果消息采用单条 assistant 消息容器，视觉宽度应比普通短文本气泡更适合承载结构化内容，但不应横向铺满到破坏 Chat 阅读节奏。容器内部顺序固定为：

1. 任务摘要头部：显示采集完成状态、平台、主题或关键词、结果数量。
2. AI 总结回答区：使用通用 Markdown 渲染。
3. 采集结果操作区：显示统计、分组概览、结果列表和操作按钮。

采集结果操作区行为：

- 默认展示前若干条结果。
- 超出默认展示数量时显示“展开查看全部”。
- 展开后显示全部结果，并提供“收起”。
- 每条结果显示勾选框、标题、可用元信息和打开原链接操作。
- 顶部显示“已选 X / N 条”。
- 顶部显示“全选 / 取消全选”和“导入已选”操作。
- 分组标签只展示统计，不响应点击筛选。
- 不显示搜索框、平台筛选、分组筛选。

状态反馈：

- 导入成功：显示新增数量和跳过重复数量。
- 无可导入条目：显示明确反馈。
- 单条缺少 URL：隐藏该条打开操作。
- 结果为空：不展示空操作区，保留 AI 总结或空结果说明。

Chat 可靠 SSE 运行交互：

- 创建运行中：发送按钮进入 loading 或 disabled 状态，消息流中显示轻量“正在连接 AI”状态。
- 运行中：工具过程、采集结果和 AI 文本 chunk 按事件流逐步更新；已有内容不得因重连被清空。
- 自动重连中：保留当前已收到文本、工具步骤和采集结果，显示非阻塞的“正在恢复连接”提示。
- 页面刷新恢复：如果本地存在未完成运行记录，先查询运行状态；运行中继续订阅，已完成直接展示最终任务结果，已过期则清理本地记录并提示可重新发送。
- 收到 `done`：将本轮已收集的 AI 文本、采集结果和最终 `reply` 组合为一条 assistant 任务结果消息。
- 收到 `chat_error`：显示错误信息，不把部分流式内容写成最终 assistant 消息。
- 收到 `canceled`：停止订阅，显示取消状态，保留已收到内容作为临时上下文但不提交为最终消息。
- 超过约定恢复超时仍无新事件：进入 interrupted 状态，保留已收到内容，并提供重新发送或继续恢复的入口；具体入口样式在 plan 阶段确定。

## 数据模型（Data Model）

本功能围绕 Chat 消息渲染模型展开，预计需要在现有 Chat 消息结构中表达“同一条 assistant 消息包含通用文本和平台采集结果”的关系。

现有相关概念：

- `ChatMessage.role`: 当前包含 `user`、`assistant`、`tool`、`collect`。
- `ChatCollectResult`: 当前包含 `platform`、`topic`、`items`。
- `ChatCollectItem`: 当前包含 `title`、`url`、`excerpt`、`metric`、`author`。

目标数据表达：

- 一条 assistant 任务结果消息应能同时携带：
  - AI 总结文本。
  - 0 个或多个平台采集结果集合。
  - 每个集合的平台、主题、结果数量和条目列表。
- 采集条目至少应支持：
  - 标题。
  - URL。
  - 摘要或简短说明。
  - 平台来源。
  - 可选指标。
  - 可选作者。
  - 可选分组标签或分类名。

如果实现阶段发现当前 `ChatCollectItem` 已能覆盖最小展示和导入需求，可以不新增后端字段；如果需要分组统计，应优先使用工具返回的现有字段或前端可稳定推导的字段。不得为了分组统计引入新的 LLM 二次分类流程，除非后续 spec 单独确认。

新增 Chat 对话运行模型：

### ChatConversationRun

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | string | 对话运行唯一标识，对外暴露为 `runId` |
| `session_id` | string | 所属 Chat session，对外使用 `sessionId` |
| `status` | `"pending" \| "running" \| "done" \| "error" \| "canceled"` | 对话运行生命周期 |
| `message` | string | 用户本轮输入快照 |
| `events` | `ChatSseEvent[]` | 可恢复业务事件缓存 |
| `reply` | string | 完成后的最终 AI 回复 |
| `collect_results` | `ChatCollectResult[]` | 本轮平台采集结果集合，对外使用 `collectResults` |
| `error` | string 或 null | 失败原因 |
| `created_at` | datetime | 创建时间，对外使用 `createdAt` |
| `updated_at` | datetime | 最近更新时间，对外使用 `updatedAt` |
| `expires_at` | datetime 或 null | 终态运行过期时间，对外使用 `expiresAt` |

### ChatSseEvent

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | number | 运行内递增业务事件 id |
| `event` | `"tool_start" \| "tool_end" \| "collect_result" \| "chunk" \| "done" \| "chat_error" \| "canceled"` | 标准 SSE event 名称 |
| `data` | object | 事件负载 |
| `created_at` | datetime | 事件创建时间，对外使用 `createdAt` |

### 前端 Chat 运行恢复状态

| 字段 | 类型 | 说明 |
|---|---|---|
| `runId` | string | 当前未完成或待恢复的对话运行 |
| `sessionId` | string | 所属 Chat session |
| `lastEventId` | number | 已应用的最后业务事件 id |
| `streamingContent` | string | 已收到的 AI 文本 chunk |
| `toolSteps` | string[] | 已收到的工具过程文案 |
| `collectResults` | `ChatCollectResult[]` | 已收到的平台采集结果 |
| `status` | `"creating" \| "streaming" \| "recovering" \| "done" \| "error" \| "interrupted" \| "canceled"` | 前端运行阶段 |
| `error` | string 或 null | 可展示错误 |

## 接口设计（API / Interface Design）

本 spec 要求新增 Chat 对话运行相关 API，并保留旧 Chat 流式接口的兼容空间。所有非 SSE JSON 接口必须使用项目统一响应 envelope：成功为 `{"ok": true, "data": ...}`，失败为 `{"ok": false, "error": {"message": "..."}}`。字段对前端使用 camelCase。

预期接口边界：

- 后端 Chat 对话运行创建接口负责接收用户消息并启动后台对话运行。
- 后端 Chat 对话运行订阅接口负责发送标准 SSE 字段 `id`、`event`、`data`。
- 后端 Chat 对话运行查询接口负责页面刷新恢复和终态读取。
- 后端流式接口负责发送 AI 文本 chunk、工具过程事件和平台采集结果事件。
- 前端消息组装层负责把同一轮对话中的 AI 总结和平台采集结果组合为一条任务结果消息。
- 历史消息读取接口应能重建与实时流式阶段一致的任务结果消息结构。
- 工作台导入行为继续复用现有前端 store 或导入逻辑，不新增单独导入 API。

接口设计：

| 接口 | 方法 | 请求/响应 | 说明 |
|---|---|---|---|
| `/api/agent/conversation/runs` | POST | 请求 `{ sessionId, message }`；响应 data `{ runId, status }` | 创建对话运行并立即返回 |
| `/api/agent/conversation/runs/{runId}` | GET | 响应 data 为运行快照，包含 `status`、`reply`、`collectResults`、`error`、`lastEventId`、`expiresAt` | 页面刷新恢复和终态查询 |
| `/api/agent/conversation/runs/{runId}/stream` | GET | 标准 `text/event-stream` | EventSource 订阅；支持 `Last-Event-ID` 和 `?lastEventId=` |
| `/api/agent/conversation/runs/{runId}` | DELETE | 响应 data `{ runId, status: "canceled" }` | 取消未完成对话运行 |

SSE 事件契约：

| event | 是否带 id | data | 说明 |
|---|---|---|---|
| `tool_start` | 是 | `{ "text": "...", "name": "..." }` | 工具开始执行 |
| `tool_end` | 是 | `{ "text": "...", "name": "..." }` | 工具执行结束 |
| `collect_result` | 是 | `{ "platform": "...", "topic": "...", "items": [...] }` | 平台采集结果 |
| `chunk` | 是 | `{ "text": "..." }` | AI 文本增量 |
| `done` | 是 | `{ "reply": "...", "collectResults": [...] }` | 本轮对话运行完成 |
| `chat_error` | 是 | `{ "message": "..." }` | 业务失败 |
| `canceled` | 是 | `{ "message": "..." }` | 用户或系统取消 |
| `heartbeat` | 否 | `{ "ts": "ISO-8601 string" }` | 保活，不写入恢复缓存 |

示例事件格式只用于说明协议形状：

```text
id: 1
event: tool_start
data: {"text":"开始调用 zhihu_search","name":"zhihu_search"}

id: 2
event: collect_result
data: {"platform":"zhihu","topic":"个人网站搭建","items":[{"title":"如何自己搭建一个个人网站？","url":"https://www.zhihu.com/question/1"}]}

id: 3
event: chunk
data: {"text":"采集完毕。"}

id: 4
event: done
data: {"reply":"采集完毕。","collectResults":[...]}
```

如果实现阶段需要调整 `ChatMessage` 前端类型，应保持向后兼容：

- 普通 `assistant` 文本消息仍能只包含 `content`。
- 平台采集任务消息可以在同一消息上携带结构化采集结果。
- 旧的 `collect` 角色历史数据如仍存在，应有兼容渲染或迁移策略，不能导致历史页面空白。

## 架构说明（Architecture Notes）

当前 Chat 渲染的问题不是单个卡片样式问题，而是消息结构层级问题：一次 AI 任务被拆成多个同级消息，导致用户无法把“过程、结果、总结”理解为同一次回答。

新的设计应以“任务结果消息”为 Chat 渲染单元：

- AI 总结是主阅读内容。
- 平台采集结果是同一消息中的操作区。
- 工具过程是低优先级过程信息，不进入专用结果操作区。
- Chat 对话运行是可靠 SSE 的恢复单元，负责缓存工具事件、采集结果事件、AI 文本 chunk 和终态事件。

与现有系统集成时应注意：

- `ChatPage` 当前在流式完成时将 `tool`、`collect`、`assistant` 分别追加到 `messages`。实现阶段需要重新设计同一轮事件的聚合策略。
- `ChatMessageThread` 当前按 `message.role` 直接分支渲染。实现阶段需要支持包含结构化结果的 assistant 任务消息。
- `ChatCollectResultCard` 当前承担采集结果展示和导入工作台功能。实现阶段可复用其导入逻辑和条目转换逻辑，但视觉和容器层级应调整为任务结果消息内部的结果操作区。
- 历史重建逻辑需要与实时流式逻辑保持一致，避免刷新后又回到“工具消息、采集卡片、AI 气泡”三段式。
- 现有 `/api/agent/conversation/stream` 使用旧式 `data.type` 协议。实现阶段应新增可靠 SSE run 接口，并让 Chat 页面默认使用新接口；旧接口可以保留以降低迁移风险。
- Chat 可靠 SSE 运行模型可以参考工作台可靠 generation job 的 `id/event/data`、事件缓存、`Last-Event-ID` 和 `lastEventId` 恢复语义，但不能复用工作台生成 job 的 `item`、`answer`、编辑器草稿等领域状态。
- 对话运行完成后，最终消息仍应写入 LangGraph 对话历史；运行缓存只负责连接恢复和短期补发，不替代长期历史存储。

## 测试策略（Testing Strategy）

前端组件测试：

- 覆盖任务结果消息同时渲染 AI 总结和采集结果区。
- 覆盖普通 assistant 消息仍只渲染 Markdown。
- 覆盖结果列表默认折叠、展开全部、收起。
- 覆盖单选、取消选择、全选、取消全选。
- 覆盖导入已选调用工作台导入逻辑，并显示新增和重复跳过反馈。
- 覆盖缺少 URL 的条目不显示打开原链接。
- 覆盖无结果时不显示空操作区。
- 覆盖结果区不存在搜索框、平台筛选和分组筛选控件。

前端状态与集成测试：

- 覆盖流式事件完成后，`tool`、`collect`、`assistant` 被组合成一条任务结果消息。
- 覆盖历史消息读取后，页面渲染结构与实时流式完成后的结构一致。
- 覆盖多个采集结果集合在同一轮对话中的展示顺序和导入行为。
- 覆盖创建对话运行后，通过 `EventSource` 应用 `tool_start`、`tool_end`、`collect_result`、`chunk`、`done` 事件。
- 覆盖 `id <= lastEventId` 的重复事件被忽略。
- 覆盖页面刷新后使用本地保存的 `runId` 和 `lastEventId` 恢复订阅。
- 覆盖 `EventSource.onerror` 只进入恢复状态，不立即把运行标记为失败。
- 覆盖收到 `chat_error` 后显示错误并清理或保留本地运行状态。

后端测试：

- 测试对话运行创建接口返回统一 envelope 和 `runId`。
- 测试对话运行事件 id 单调递增，`heartbeat` 不占用业务 id。
- 测试带 `Last-Event-ID` 订阅时只补发缺失业务事件。
- 测试带 `?lastEventId=` 订阅时能补发刷新后缺失事件。
- 测试订阅已完成运行时补发到 `done` 后关闭连接。
- 测试运行失败时发送 `chat_error`，不发送业务 `error`。
- 测试运行取消时发送 `canceled`，后台后续 token 不再更新该运行。
- 测试 `_build_history_messages` 或对应消息构建函数能输出统一任务结果结构。

验收标准映射：

- 验收标准 1、15、16 对应 Chat 消息渲染组件测试。
- 验收标准 3、4、5、9、10 对应结果区交互测试。
- 验收标准 6、11 对应 URL 操作测试。
- 验收标准 7、12、13、14、17 对应结果区布局和边界测试。
- 验收标准 8 对应分组标签只读展示测试。
- 验收标准 18、19、20、21 对应 Chat 可靠 SSE 正常流式测试。

## 风险（Risks）

- 实时流式消息与历史消息重建若使用两套聚合逻辑，可能出现刷新前后渲染不一致。
- 如果结果数量很大，inline 面板可能仍会使 Chat 列表变长，需要默认折叠和收起行为兜底。
- 当前平台工具返回字段不完全一致，结果区必须能优雅处理缺少摘要、作者、指标或 URL 的条目。
- 如果导入逻辑与工作台去重逻辑没有复用，可能出现重复导入或反馈不一致。
- 如果为了分组统计临时引入不稳定推导，可能造成分组标签误导用户；没有可靠分组时应隐藏分组标签。
- 旧历史消息可能已经包含独立 `collect` 角色，需要兼容处理。
- Chat 对话运行引入后台执行和事件缓存后，实时流式、短期运行缓存、长期 LangGraph 历史之间可能出现状态不一致，需要明确完成写入顺序。
- EventSource 只能使用 GET，不能直接携带 POST body；因此 Chat 需要创建运行接口和订阅接口两阶段流程。
- 单进程内存缓存无法跨服务重启恢复；刷新恢复只能覆盖服务仍保留运行缓存的情况。
- `EventSource.onerror` 与业务失败容易混淆；如果使用 `error` 作为业务事件名，会破坏恢复语义，必须使用 `chat_error`。
- 多工具、多平台结果在同一轮中返回时，事件顺序和最终 `done.collectResults` 必须一致，否则 UI 可能重复或漏展示结果。
