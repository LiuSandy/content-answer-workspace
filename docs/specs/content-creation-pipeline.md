# 内容创作完整流程分析与规划

> 状态：已确认 (Approved)
> 日期：2026-07-26
> 前置结论：RAG 以"检索测试面板完整"为当前边界，暂不接入聊天主链路；
> 本文档分析内容创作主流程的缺失环节，作为后续功能规划依据。

## 1. 现状

```
现有流程：  采集 ──→ 选帖 ──→ AI 生成回答 ──→ 手动编辑/润色 ──→ 存在本地
                                 ↑
                          大模型唯一的角色：写手
```

这是一条**只有中段的流水线**：上游没有决策，下游没有出口，没有反馈回流。
对照真实内容创作者的完整工作流，缺失五层能力。

已具备的资产（后续规划应复用，不重建）：

| 资产 | 位置 | 状态 |
|------|------|------|
| 多平台采集（知乎/小红书/Reddit/GitHub/V2EX 等） | `infrastructure/sources/` + agent tools | 可用 |
| 回答生成/重写/润色三条工作流 | `app/workflows/` | 可用 |
| 版本系统（AI 版 vs 手动编辑版 + 乐观锁 + AI Operation 审计） | `persistence/models/documents.py` | 可用但数据未被利用 |
| Prompt Registry（YAML + model profiles） | `app/prompts/` | 可用 |
| 私有知识库 RAG（混合检索 + 重排 + Trace） | `application/knowledge/` | 检索测试面板完整 |
| 热榜页 | `frontend/features/hotlist/` | 仅展示，无分析 |

## 2. 缺失的五层

### 2.1 选题决策层（上游，完全缺失）

**问题**：采集回来 50 个问题，答哪个？现在靠人肉浏览挑选。

真实创作者的核心决策是"值不值得答"：

- **流量潜力**：浏览量/回答数比（高浏览低回答 = 蓝海）、热度趋势（在涨还是在凉）
- **竞争分析**：现有高赞回答的质量与角度，能否打出差异化
- **匹配度**：与账号定位/擅长领域的相关性

采集时浏览量、回答数等原始数据大部分已抓到，但没有任何分析环节。

**大模型新角色：选题分析师** —— 批量给采集结果打"值得答指数"+ 一句话理由，
把 50 个问题变成排好序的 5 个。热榜页是雏形，缺评估层。

### 2.2 观点注入层（创作前，完全缺失——最致命）

**问题**：当前生成 = 问题 + 风格规则 → 回答，内容全部来自模型参数。
产出必然是"正确的平均废话"——所有用 AI 写回答的人产出同质内容，
平台和读者一眼识别，没有获得赞同的理由。

真实的好回答 = **独特的观点/经历/证据** + 好的表达。缺失环节：

- **观点采集**：生成前先问用户 2~3 个问题（"你对这个问题的真实看法？
  有没有亲身经历？"），把人的观点作为素材注入 prompt。
  AI 负责表达，人负责观点。
- **素材库**：用户的案例、数据、金句积累。
  **这是已建成的 RAG 基础设施的真正用途**——私有知识库里存的不该只是
  资料文档，更该是"我的素材"。RAG 未来的接入点在这里，而非普通闲聊。

### 2.3 质量保障层（创作后，完全缺失）

**问题**：生成完直接进编辑器，没有任何质检。

**大模型新角色：审稿人**（成本最低、见效最快的一环）：

- **AI 味检测**："作为一个……""总的来说……"等模式化表达识别与改写建议
- **平台合规**：违禁词、广告法用语、平台调性（知乎反感营销腔）
- **质量评分**：钩子强度（前三行能否留住人）、结构、信息密度。
  LLM-as-judge 打分 + 具体修改建议，低于阈值提示重写。

### 2.4 发布与状态层（下游出口，完全缺失）

**问题**：回答写完后的终点是"存在数据库里"，没有出口。

- **发布工作台**：已发布 / 待发布 / 草稿状态管理，一键复制
  （带平台格式适配——知乎与小红书格式不同）
- **发布记录**：发布时间 + 回答 URL 回填（手动粘贴即可，不做自动发布）

没有这层，反馈回流层无从谈起。

### 2.5 反馈回流层（闭环，完全缺失——"生成工具"与"运营系统"的分水岭）

- **表现数据回流**：发布后的赞同/评论/涨粉。第一版手动录入即可；
  后续可用已有采集器定期抓取自己回答的数据（技术栈现成）。
- **归因分析**：什么选题、什么开头、什么风格表现好。
  **大模型新角色：数据分析师**。
- **风格学习**：当前最被浪费的资产——版本系统已存有
  "AI 生成版 vs 用户手动编辑版"的完整 diff，用户每次修改都在表达偏好。
  定期让 LLM 分析这些 diff，自动提炼/更新风格规则，越用越像本人。
  数据结构已就绪，缺分析逻辑。

## 3. 目标闭环

```
选题分析 → 观点采集 → 大纲 → 生成 → 质检 → 编辑 → 发布管理 → 数据回流
   ↑____________________________________________________________|
                    （反馈指导下一轮选题与风格）
```

大模型角色矩阵：

| 环节 | 大模型角色 | 现状 |
|------|-----------|------|
| 选题分析 | 分析师 | ❌ 缺失 |
| 观点采集 | 采访者 | ❌ 缺失 |
| 大纲 | 策划 | ❌ 缺失（spec 已有：`feature-outlines-structured-generation.md`，覆盖结构化输出与内容大纲） |
| 生成 | 写手 | ✅ 已有 |
| 质检 | 审稿人 | ❌ 缺失 |
| 编辑/润色 | 编辑 | ✅ 已有 |
| 数据分析 | 数据分析师 | ❌ 缺失 |

## 4. 各环节落地要点

### 4.1 选题评估（P2）

- 数据模型：`SourceItem` 增加评估结果字段（或独立 `TopicEvaluation` 表）：
  `worth_score`（0-100）、`reason`、`competition_level`、`evaluated_at`
- Prompt：`prompts/analysis/topic_evaluation.yml`，输入采集元数据
  （标题、浏览量、回答数、热度），输出结构化评分
- UI：采集结果列表按 worth_score 排序，展示评分徽章 + 理由 tooltip
- 复用：批量评估走现有 LLM registry，参考 `answer_generation` 工作流结构

### 4.2 观点注入 + 大纲（P4，与结构化输出与大纲 spec 合并设计）

- 流程：选帖 → LLM 生成 2~3 个采访问题 → 用户回答（可跳过）→
  观点 + 大纲 → 分段生成
- 数据模型：`AnswerDocument` 关联 `viewpoint_notes`（用户观点原文）；
  素材沉淀进知识库（`source_type=material`）
- 与 RAG 的衔接：生成时从素材库检索用户相关案例/观点注入上下文
  （这是 RAG 接入主流程的正式时机）

### 4.3 质检审稿（P1，最先做）

- 实现：新工作流 `app/workflows/quality_review.py`，输入回答全文 + 平台，
  输出结构化报告：`ai_flavor_score`、`hook_score`、`compliance_issues[]`、
  `suggestions[]`
- Prompt：`prompts/review/quality_review.yml`
- UI：编辑器侧边"质检"按钮 → 报告面板，逐条建议可一键采纳（复用润色工作流）
- 不新增表：报告作为 `AIOperation` 记录存档

### 4.4 发布状态管理（P3）

- 数据模型：`AnswerDocument` 增加 `publish_status`
  （draft / ready / published）、`published_at`、`published_url`
- UI：发布工作台视图（按状态分组）+ 一键复制（平台格式适配）
- 不做自动发布

### 4.5 风格学习（P5）

- 数据源：现有 `AnswerVersion` 中 AI 生成版与相邻手动编辑版的 diff
- 实现：定期任务（或手动触发）→ LLM 分析 diff 批次 →
  输出风格规则增量 → 用户确认后合并进 style_rules
- 关键约束：必须经用户确认，不静默改写风格规则

### 4.6 数据回流分析（P6，依赖 4.4 积累数据）

- 数据模型：`PublishMetrics` 表（answer_document_id、抓取时间、
  赞同/评论/收藏数）
- 采集：复用现有平台采集器抓自己的回答页
- 分析：LLM 汇总"高表现内容的共性"报告，反哺选题评估与风格规则

## 5. 优先级与依赖

| 优先级 | 功能 | 理由 | 依赖 |
|--------|------|------|------|
| P1 | 质检审稿 | 一个 prompt + 一个面板，立刻提升出品质量 | 无 |
| P2 | 选题评估 | 数据现成，只加分析层，省掉最耗时的人肉筛选 | 无 |
| P3 | 发布状态管理 | 很薄的 CRUD，但是闭环的开关 | 无 |
| P4 | 观点注入 + 大纲 | 差异化的根本；RAG 正式接入主流程的时机 | 结构化输出与大纲 spec |
| P5 | 风格学习 | 利用已有版本 diff，独特杠杆 | 无（数据已在积累） |
| P6 | 数据回流分析 | 闭环收口 | P3 积累数据 |

## 6. 明确不做

- 自动发布（合规与账号安全风险）
- 多账号矩阵管理（当前为个人单账号工具）
- 实时协同编辑
- RAG 接入聊天主链路（推迟到 P4 观点注入时以"素材库"形态接入）
