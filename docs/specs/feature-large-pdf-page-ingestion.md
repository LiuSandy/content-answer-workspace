# 大型 PDF 逐页识别与断点恢复

## 1. 背景

现有源文件摄取流程适合普通 PDF，但无法可靠处理 70MB 以上、300 页以上的大型 PDF：

- 文件大小默认限制为 50MB；
- 哈希和解析会一次性读取整个文件；
- PDF 识别阶段缺少页级状态和真实进度；
- 服务中断后只能重新执行整份 PDF；
- 单页失败会使整份文件识别失败。

本功能只改造大型 PDF 从源文件进入候选 Markdown 的识别阶段。候选 Markdown 的人工确认、正式 Markdown、分块、Embedding、索引和 RAG 检索保持不变。

## 2. 目标

大型 PDF 识别必须满足：

1. 支持至少 2GB 的源 PDF，不因当前 50MB 限制直接失败。
2. 上传、哈希和识别过程中不一次性将整个 PDF 读入 Python 内存。
3. 每次只提取并转换一页，页面结果独立持久化。
4. 前端显示总页数、已完成页数、成功页数、失败页数和真实进度。
5. 页面刷新不影响任务；服务终止并重启后不重做已经成功的页面。
6. 单页失败不阻止其他页面继续处理。
7. 全部页面处理结束后按页码合并候选 Markdown，并进入现有人工确认流程。

## 3. 非目标

- 不改造候选 Markdown 的人工确认流程。
- 不改造现有分块、Embedding、索引和 RAG 检索。
- 不增加前端配置页面。
- 不增加复杂的 PDF 页面管理器或人工逐页编辑器。
- 不在本期支持 Word、PowerPoint、Excel 等新格式。
- 不实现跨机器分布式任务调度。

## 4. 总体流程

```text
前端流式上传 / pending 目录投放
                 ↓
      文件稳定性检查与流式 SHA-256
                 ↓
          格式、大小和重复校验
                 ↓
        pending → processing
                 ↓
       按文件路径打开 PDF，读取页数
                 ↓
          创建逐页持久化任务
                 ↓
   每次提取一页 → 转换 Markdown → 立即落盘
                 ↓
       全部页面结束后按页码合并
                 ↓
 recognized / awaiting_confirmation
```

## 5. 大文件接收与校验

### 5.1 文件大小

新增配置：

```text
KNOWLEDGE_MAX_SOURCE_FILE_BYTES=2147483648
```

默认最大值为 2GB。前端上传与目录扫描使用相同上限。

超过上限的文件进入：

```text
failed / file_too_large
```

### 5.2 前端上传

上传接口必须按固定大小缓冲区循环读取，例如每次 4MB：

```text
读取数据块 → 写入 .uploading 临时文件 → 更新 SHA-256 → 累加大小
```

完整写入、刷新文件并校验成功后，原子重命名到 `pending/`。不得调用无上限的整文件 `read()` 或 `read_bytes()`。

### 5.3 目录扫描

目录投放的文件通过稳定性检查后，使用固定大小缓冲区流式计算 SHA-256。哈希阶段不得把整个文件读入内存。

文件任务在哈希阶段保存：

- 已读取字节数；
- 文件总字节数；
- 哈希阶段进度。

所有文件继续使用现有内容哈希去重规则。重复文件进入 `failed / duplicate_source`，不创建页面任务。

## 6. PDF 逐页处理

### 6.1 按文件路径打开

执行器使用源文件路径打开 PDF：

```python
fitz.open(source_path)
```

不得先把完整 PDF 读取为 bytes 再打开。

### 6.2 单页提取

处理第 N 页时：

1. 从源 PDF 读取第 N 页；
2. 创建只包含该页的临时 PDF；
3. 调用现有 PDF 转换能力生成单页 Markdown；
4. 将 Markdown 原子写入页面结果文件；
5. 保存页面状态、置信度和错误；
6. 清理该页临时 PDF。

任何转换请求或本地解析单元都不得包含多页。

### 6.3 中间产物目录

```text
output/knowledge/ingestion-work/<job-id>/
├── pages/
│   ├── 000001.md
│   ├── 000002.md
│   └── ...
└── temporary/
```

页面 Markdown 在服务重启后继续作为已完成页面的恢复依据。临时单页 PDF 在每页处理结束后立即删除。

### 6.4 并发限制

继续保留全局最多同时处理 2 个源文件。

同一 PDF 内的页面识别默认并发为 1，严格做到一页完成后再处理下一页：

```text
KNOWLEDGE_PDF_PAGE_CONCURRENCY=1
```

该值只允许通过环境变量调整，本期不提供配置页面。

## 7. 页面任务持久化

新增 `knowledge_ingestion_pages` 表：

| 字段 | 说明 |
|---|---|
| `id` | 页面任务 ID |
| `job_id` | 所属文件摄取任务 |
| `page_number` | 从 1 开始的页码 |
| `status` | `pending / running / succeeded / failed` |
| `attempt_count` | 已尝试次数 |
| `markdown_path` | 单页 Markdown 路径 |
| `content_hash` | 单页 Markdown SHA-256 |
| `confidence` | 单页识别置信度 |
| `error_code` | 稳定错误码 |
| `error_message` | 用户可读错误 |
| `lease_owner` | 页面执行器实例 |
| `lease_expires_at` | 页面任务租约时间 |
| `started_at` | 开始时间 |
| `completed_at` | 完成时间 |
| `created_at / updated_at` | 时间戳 |

数据库约束：

```text
UNIQUE(job_id, page_number)
```

文件摄取任务增加汇总字段：

- `total_pages`
- `completed_pages`
- `succeeded_pages`
- `failed_pages`
- `current_page`

页面状态是恢复依据，汇总字段用于前端快速查询。

## 8. 进度

进度按实际阶段计算：

| 阶段 | 范围 |
|---|---:|
| 稳定性检查 | 0–2% |
| 流式哈希和去重 | 2–8% |
| PDF 元数据和页面任务初始化 | 8–10% |
| 逐页识别 | 10–90% |
| 页面 Markdown 合并 | 90–98% |
| 保存候选稿 | 98–100% |

逐页识别阶段：

```text
progress = 10 + 已结束页数 / 总页数 × 80
```

“已结束页数”包含成功页面和达到最终失败状态的页面。

前端至少显示：

```text
正在逐页识别 PDF
已完成 183 / 326 页
成功 181 页 · 失败 2 页
```

页面刷新后通过数据库重新获取这些统计，不依赖前端内存。

## 9. 页面失败

### 9.1 自动重试

每页最多尝试 3 次。临时网络错误、远程解析超时等可恢复错误采用延迟重试；页面损坏、源文件丢失或源文件哈希变化等不可恢复错误不自动重试。

### 9.2 不阻断整份文件

单页最终失败后，继续处理后续页面。

全部页面结束时：

- 至少一页成功：合并候选 Markdown，任务状态为 `completed_with_errors`；
- 所有页面失败：文件任务进入 `failed / recognition_failed`，不生成候选 Markdown。

失败页在候选 Markdown 中生成占位内容：

```markdown
<!-- source-page: 127 -->

> 第 127 页识别失败，请在确认前人工补充。
```

前端明确显示“识别完成，但有 N 页失败”。

## 10. 服务重启恢复

服务启动后：

1. 恢复租约过期的文件任务和页面任务；
2. 验证源 PDF 仍存在且内容哈希没有变化；
3. 查询 `knowledge_ingestion_pages`；
4. 跳过 `succeeded` 页面；
5. 将租约过期的 `running` 页面恢复为 `pending`；
6. 继续处理尚未结束的页面；
7. 所有页面结束后幂等执行 Markdown 合并。

服务在第 N 页中断时，只允许重做当时处于 `running` 的单页，不得重做此前已经成功的页面。

若源 PDF 在处理期间被修改，任务进入 `failed / source_changed`，不得把新旧页面结果混合。

## 11. Markdown 合并

页面结果严格按 `page_number` 排序，每页添加稳定页边界：

```markdown
<!-- source-page: 1 -->

第一页内容

---

<!-- source-page: 2 -->

第二页内容
```

合并先写入临时候选文件，完整写入并刷新后再原子替换正式候选 Markdown。合并操作必须幂等，可在服务重启后安全重做。

单页 Markdown 在候选稿等待确认期间保留。用户确认候选 Markdown 或删除资料后，系统清理该任务的页面中间产物。

## 12. API 与前端数据

现有文档和源文件接口增加以下摄取统计：

```json
{
  "totalPages": 326,
  "completedPages": 183,
  "succeededPages": 181,
  "failedPages": 2,
  "currentPage": 184,
  "progressPercent": 54
}
```

前端只增加核心状态展示：

- 当前处理阶段；
- 总页数；
- 已完成页数；
- 成功页数；
- 失败页数；
- 总进度；
- 完成后是否存在失败页。

本期不增加逐页管理界面。

## 13. 清理规则

- 单页临时 PDF：该页处理完成后立即删除。
- 单页 Markdown：候选稿确认或资料删除后清理。
- 任务失败时保留成功页面 Markdown，便于诊断和恢复；资料删除时统一清理。
- 清理操作失败只记录日志并允许下次启动重试，不回滚已确认的知识文档状态。

## 14. 验收标准

使用一份 70MB 以上、300 页以上的真实 PDF 验证：

1. 文件可以通过前端上传或 `pending/` 目录进入任务，不因 50MB 限制失败。
2. 上传和哈希使用固定缓冲区，内存占用不随文件大小等比例增长。
3. 每个页面转换单元只包含一页。
4. 前端显示总页数、已完成、成功、失败和真实进度。
5. 服务终止并重启后，已成功页面不再转换。
6. 中断时正在处理的单页可以安全重做。
7. 单页失败不阻断剩余页面。
8. 最终候选 Markdown 严格按页码顺序合并。
9. 失败页在候选 Markdown 中有明确占位。
10. 用户确认前，候选 Markdown 不进入分块和索引。
11. 全局仍最多同时处理 2 个源文件；单个 PDF 默认逐页串行处理。
