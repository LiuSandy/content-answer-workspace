# 知乎功能对照表

本文基于知乎公开开发者文档，整理你们当前项目能力与官方能力的对应关系。

来源：

- [知乎开发者文档首页](https://developer.zhihu.com/docs)
- [知乎开发者文档索引接口](https://developer.zhihu.com/console/api/v2/docs)

## 对照表

| 你们现有功能 | 当前实现 | 官方能力 | 可替代性 | 建议 |
| --- | --- | --- | --- | --- |
| 按主题采集知乎问题 | 目前走 `search_v3`，依赖 cookie、`x-zse-93`、`x-zse-96`，并在本地做关键词过滤与去重 | `知乎搜索 API / Skill / MCP` | 可部分替代 | 优先迁移到官方知乎搜索；你们自己的主题扩词、去重、结果裁剪逻辑继续保留 |
| 单个知乎问题链接导入 | 目前通过 URL 提取问题 ID，再抓详情接口和网页 HTML 兜底 | 官方文档当前公开能力里没有明确列出“按问题 URL/ID 取详情”的独立接口 | 暂不能完整替代 | 继续保留现有导入逻辑；如后续官方开放详情接口，再单独接入 |
| 热门内容/热点补充 | 当前没有独立的热榜接入 | `知乎热榜 API / Skill / MCP` | 可直接新增 | 建议新增“热榜采集”入口，用作选题补充和热点发现 |
| 站外补充资料搜索 | 当前没有平台级全网搜索接入 | `全网搜索 API / Skill / MCP` | 可直接新增 | 可作为扩展能力，不替代知乎站内采集本身 |
| AI 扩展检索词 | 目前用 DeepSeek 做主题扩词 | 官方没有同类“扩词”API | 不需要替代 | 保留；这层属于你们自己的检索增强逻辑 |
| 生成回答 | 目前用你们自己的模型链路生成内容 | `直答 API / Skill / MCP` | 可部分替代 | 如果目标是“快速问答/解释/总结”，可考虑把直答接入为另一种生成模式；如果目标是“采集后定制化长回答”，现有模型链路更适合 |
| 内容工作台的统一入口 | 前端只做知乎单平台工作流 | 官方支持多种搜索/热榜/直答能力 | 可增强，不是替代 | 建议把“数据源”与“回答生成”拆成独立配置，支持官方 API 与现有抓取并存 |

## 如何落地这些结论

下面不是代码实现，而是落地顺序和职责边界。

### 1. 可部分替代：知乎搜索 API / Skill / MCP

你们当前的核心问题不是“能不能搜到”，而是“搜索结果是否稳定、是否需要 cookie、是否会被网页结构变化影响”。官方知乎搜索能力的价值在于把这部分风险从逆向抓取转成正式接口。

建议按下面顺序做：

1. 先保留现有抓取逻辑作为 `web` 模式，不要一次性删除。
2. 新增一个独立的数据源适配层，专门处理官方搜索接口返回值到你们内部 `QuestionItem` 的映射。
3. 让主题扩词逻辑继续保留在你们内部，因为这属于你们自己的检索策略，不属于官方能力。
4. 把采集入口改成“数据源可选”，至少支持 `official`、`web`、`auto` 三种模式。
5. `auto` 模式优先走官方搜索，失败时回退到现有抓取；这样能在早期降低迁移风险。
6. 统一做字段映射和去重，保证前端不需要关心数据来自官方还是网页。

你们真正要保留的部分是：

- 主题扩词
- 结果去重
- 结果裁剪
- 生成回答前的筛选
- 前端工作台的统一展示模型

你们真正可以替换掉的部分是：

- cookie 依赖
- `x-zse-93` / `x-zse-96` 逆向签名
- 网页结构解析兜底
- 非稳定搜索请求路径

如果后续官方只开放“站内搜索”，但不开放“问题详情”，那也不影响你们先迁移搜索入口。问题详情可以继续保留现有 URL 导入兜底，二者可以长期并存。

### 2. 可直接新增：知乎热榜 API / Skill / MCP

热榜能力不是替代你们现有采集，而是补充一个新的内容入口。它最适合做三件事：

- 找近期热门话题，作为选题源
- 为当前主题补充趋势性内容
- 帮前端做“热点推荐”模块

建议这样接：

1. 新增一个独立入口，不要塞进现有“按主题采集”流程里。
2. 热榜数据模型要单独定义，至少保留 `title`、`url`、`thumbnail_url`、`summary`。
3. 前端可以提供一个“热榜”标签页，和当前“主题采集”并列。
4. 热榜条目可以作为候选题目导入工作台，再走你们现有的回答生成流程。
5. 如果后续想做自动化，可以把热榜当成“每日选题池”，定时拉取并缓存最新内容。

热榜更适合偏产品化的扩展，而不是替代现在的搜索逻辑。因为你们当前流程强调的是“围绕主题找问题”，热榜强调的是“围绕热点找内容”，两者定位不同。

### 3. 可直接新增：全网搜索 API / Skill / MCP

全网搜索不是知乎站内功能的替身，它更适合做外部资料补强。

适合的使用场景：

- 需要把知乎问题和外部资料一起参考时
- 某个主题在知乎内结果不足时
- 想自动补充站外事实来源、项目案例、新闻或文档链接时

建议这样接：

1. 把它作为“辅助检索”而不是主采集入口。
2. 在数据结构上允许它输出和知乎不同的来源类型，避免强行混成同一类结果。
3. 前端可以把它放在“参考资料”区，而不是“待回答问题”区。
4. 若你们后续做回答生成，可以把全网搜索结果作为上下文材料，而不是直接当作题目列表。
5. 如果主题本身就是站外信息密集型，优先调用全网搜索，再决定是否回到知乎站内搜索。

全网搜索最有价值的地方在于“补盲区”，不是替代当前主题采集。它和知乎搜索的关系是互补，不是互斥。

### 4. 可增强，不是替代：直答 API / Skill / MCP

直答能力本质上是“官方回答生成通道”，更接近你们现在的模型生成能力，但它不等于你们现有的创作链路。

建议把直答当成一个新的生成模式，而不是替换你们当前的生成引擎。原因是：

- 你们现在的生成链路包含了自定义提示词、图片生成、结果编辑、会话保存
- 直答更适合快速问答、解释、总结、即时回答
- 你们的工作台更像“采集 + 编辑 + 发布前整理”，不是纯问答机器人

推荐做法：

1. 把生成能力拆成两种模式：`editorial` 和 `zhida`。
2. `editorial` 继续走现有模型链路，保留你们对文风、结构、图片、CTA 的控制。
3. `zhida` 作为官方直答模式，适合快速生成短答案、摘要、解释版内容。
4. 前端增加一个生成方式选择，但默认仍使用现有模式。
5. 如果用户只想快速看一个“可用答案”，可以优先用直答；如果用户要输出成品内容，就回到现有链路。

直答适合增强吞吐和响应速度，不适合直接替代你们当前偏内容生产的工作流。

### 5. 内容工作台的统一入口：如何拆分而不打碎现有体验

你们现在的问题不是功能少，而是采集和生成耦合得太紧。最稳妥的改法是把它拆成两层：

- 第一层：数据源层，负责拿内容
- 第二层：创作层，负责生成和编辑

这样做的好处是：

- 官方 API 可以接入
- 现有网页抓取可以保留
- 热榜、全网搜索、直答可以按需加入
- 前端不需要知道数据来自哪里，只需要知道当前结果能不能继续生成

建议的产品层能力是：

1. 数据源下拉选择：知乎搜索、热榜、全网搜索、网页导入。
2. 生成模式选择：现有创作模式、直答模式。
3. 统一的结果列表：只要能映射成 `QuestionItem`，就都能进入工作台。
4. 单独的来源标识：让用户知道一条内容来自哪里，便于筛选和回溯。

## 推荐迁移顺序

如果你们要动手，我建议顺序是：

1. 先接入 `知乎搜索 API`，把现有搜索采集做成可切换模式。
2. 再新增 `知乎热榜`，作为补充选题入口。
3. 然后接 `全网搜索`，用于扩展参考材料。
4. 最后评估 `直答` 是否作为第二生成模式引入。

这个顺序的理由很简单：

- 搜索是你们当前最核心的采集入口
- 热榜最容易做产品扩展
- 全网搜索偏辅助能力
- 直答最适合做增强，不适合先替换主链路

## 结论

如果只看你们当前项目，官方平台最值得优先接入的是：

1. `知乎搜索 API / Skill / MCP`
2. `知乎热榜 API / Skill / MCP`
3. `直答 API / Skill / MCP`

其中，`知乎搜索` 更接近你们当前的采集入口，最适合先做替换或并行支持；`热榜` 更适合新增功能；`直答` 更适合补充生成能力，而不是直接替换你们现有“采集后生成”的工作流。

目前公开文档里没有看到一个明确等价于“按知乎问题 URL 直接拉详情”的官方接口，所以你们的 URL 导入能力短期内建议保留网页抓取兜底。
