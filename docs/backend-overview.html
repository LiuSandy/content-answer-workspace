整体分层 架构

先看最外层的边界：前端只通过 HTTP 跟后端打交道，从不直接碰采集器或 LLM；后端内部严格"从上往下"递进，路由 → 编排 → 平台/服务 → 基础设施，没有跨层乱跳的调用。下图把一次请求的完整往返标了号，照着 1→2→3→4 看即可。

四层各自装了什么（细节看下面对应小节和模块速查表）

① 路由层5 个 FastAPI 路由文件：workflow（采集/生成/润色/链接导入）、agent（AI 对话）、session（会话存取）、hotlist（热榜）、config（初始配置）。统一返回 { ok, data } / { ok, error }，不包含任何业务判断。
② 编排层两个互相独立的编排者：WorkflowService 负责"采集 + 生成"这条主线；Agent Graphs（LangGraph）负责"回答精修对话"和"热榜趋势分析"两个轻量交互。
③ 平台与服务层CollectorFactory 按平台选出具体采集器（知乎网页版/官方 API、小红书、或配置驱动的通用采集器）；answer_service 统一封装"生成正文 + 生成配图"；另有 session_service（本地会话持久化）、hotlist_service（热榜）等支持性服务。
④ 基础设施层真正发起外部请求的地方：DeepSeek 客户端（所有 LLM 调用的唯一出口）、知乎官方 API 客户端、以及两种抓取器（HttpFetcher / PlaywrightFetcher）。

主题采集流程 /api/workflow/collect

用户在前端选主题、平台、采集上限后点击"开始采集"，这是一次同步阻塞的请求——LLM 扩词、平台搜索、详情补全全部在这一次调用里串行完成。

sequenceDiagram participant FE as 前端 participant API as workflow 路由 participant WS as WorkflowService participant TE as 主题扩展(LLM) participant CF as CollectorFactory participant COL as 具体采集器 FE->>API: 提交 主题 + 平台 + 来源/模式 + 采集上限 API->>WS: collect(payload) WS->>TE: 为每个主题生成检索关键词 alt LLM 扩词成功 TE-->>WS: 4~6 个扩展关键词 else LLM 调用失败 TE-->>WS: 本地规则词表兜底 end WS->>CF: create(platform, source) CF-->>WS: 对应的采集器实例 WS->>COL: collect(topics, config) COL-->>WS: 原始问题/笔记列表 WS->>WS: 按 平台+主题+ID 去重，截断到采集上限 alt 结果为空 WS-->>API: 抛出错误（不会返回空列表糊弄过去） else 有结果 WS-->>API: WorkflowResult（含本次实际用到的关键词） end API-->>FE: { ok, data }
  • 主题里保存的是"原始关键词 + AI 扩展词"的合并结果，每次点击采集都会重新问一次 LLM，所以同一主题反复采集，结果不会完全一致。
  • 整个流程没有进度条、没有轮询——前端只是发一次请求，等一次响应。

采集器是怎么被选出来的 CollectorFactory

同一个平台可能有好几种拿数据的方式（官方 API / 网页抓取 / 浏览器渲染），由 platform + source 两个参数共同决定具体走哪一条。

flowchart TD Start["CollectorFactory.create(platform, source)"] --> Q1{"source == official ?"} Q1 -->|是| Off["查找 平台:official 注册项
找不到则报错"] Q1 -->|否| Q2{"source == auto ?"} Q2 -->|是 且已配置官方密钥| OffAuto["自动使用官方采集器"] Q2 -->|是 但无密钥 / 或 source=web| Q3{"该平台有内置采集器类?"} Q3 -->|有| Built["使用内置采集器
知乎网页版 / 小红书"] Q3 -->|没有| Q4{"存在对应的 YAML 平台配置?"} Q4 -->|有| Universal["UniversalCollector
读取 YAML，HTTP/Playwright 抓取 + LLM 提取"] Q4 -->|没有| Err["抛出 不支持该平台 错误"]

这个判断逻辑全部封装在 CollectorFactory 一处，意味着：新增一个"只是想抓抓看"的平台，不用写 Python 代码，写一份 YAML（搜索 URL、认证方式、提取提示词）就能跑；而像小红书这种需要登录态 + 多阶段抓取（搜索 → 详情 → 评论）的复杂场景，才值得专门写一个采集器类。

回答生成与配图 /api/workflow/generate-one

采集只负责"拿到内容条目"，真正的创作发生在生成阶段；同一套生成入口现在按 content_mode 区分"回答问题"还是"仿写笔记"两种创作语境。

sequenceDiagram participant FE as 前端 participant API as workflow 路由 participant WS as WorkflowService participant DS as DeepSeek 生成器 participant IMG as 图片生成服务 FE->>API: 提交问题条目 + 风格 + 系统提示词 API->>WS: generate_one(payload) WS->>DS: generate_answer(item, ...) Note over DS: 按 item.content_mode 选择提示词模板：
answer → "回答问题" 话术
imitate → "仿写创作" 话术 DS-->>WS: 生成的正文 WS->>IMG: 从正文里的"配图建议"段落提炼提示词并生成图片 alt 图片相关环境变量未配置 IMG-->>WS: 降级返回空图片列表（不影响文字结果） else 配置完整 IMG-->>WS: 图片 URL 列表 + 实际使用的提示词 end WS-->>API: 更新后的问题条目（含 answer / images / imagePrompts） API-->>FE: { ok, data }

"润色"（polish-one）走的是同一套分支逻辑，只是把"从零生成"换成"基于现有草稿改写"，同样区分回答语境和仿写语境。

AI 协作层 LangGraph

除了"采集 + 生成"这条主线，还有一个基于 LangGraph 的小型状态机，处理两类更轻量的 AI 交互：在编辑区里跟 AI 对话精修当前回答，以及对知乎热榜做趋势分析。两者共用一个聊天入口，靠请求里是否带 questionId 来分流。

读取当前回答"] --> F2["apply_instruction
LLM 按用户指令定向改写"] F2 --> F3["save_answer
写回会话"] end subgraph ANA["热榜分析 Graph（进程级单例）"] H1["fetch_hotlist
拉取知乎热榜"] --> H2["analyze
LLM 输出结构化分析 JSON"] end

这一层的每个节点（fetch / apply / save / analyze）都只做一件事，互相之间通过定义好的接口（Session / LLM / Hotlist 三个"端口"）解耦，所以同一个"精修"节点不用关心 session 是存在内存里还是数据库里——目前用的是请求级内存适配器，重启或换请求就会丢失，这是当前这个交互的已知边界，不是 bug。

几个贯穿全局的设计决定

统一响应包装 camelCase 别名约定 端口/适配器解耦 配置驱动扩展 失败要报错不要吞掉
  • 统一响应包装：所有新路由返回 { ok, data } 或 { ok, error }，加上一个全局异常处理器兜底，前端不用对每个接口写不同的错误解析逻辑。
  • camelCase 别名约定：Python 内部用 snake_case，但所有模型都声明了 camelCase 别名，序列化时统一按别名输出——这样前后端字段命名风格可以各自符合自己语言的习惯，不需要谁妥协。
  • 端口/适配器解耦：采集器接口（CollectorPort）、Agent 节点依赖的接口（Session/LLM/Hotlist）都是先定义协议，再各自实现——换一个 LLM 供应商或者把 session 从内存换成数据库，只需要换适配器，不用动编排逻辑。
  • 配置驱动扩展：能用 YAML 描述清楚的平台（认证方式、搜索 URL、提取规则）就不写新代码，复杂到需要多阶段抓取或特殊反爬处理（比如小红书）才单独写采集器类——按复杂度决定要不要"上代码"。
  • 失败要报错不要吞掉：采集结果为空、cookie 失效、风控拦截，这些场景都设计成显式抛错而不是悄悄返回空列表，避免用户以为"采集成功但没内容"，实际上是配置或权限出了问题。
