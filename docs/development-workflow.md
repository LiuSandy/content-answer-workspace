# Development Workflow

本文件记录本项目使用 Superpowers、spec 和 plan 的约定。`AGENTS.md`
只保留快速操作指南，详细流程放在这里。

## 文档位置与命名

本项目使用现有目录：

- 规格文档：`docs/specs/feature-<feature-name>.md`
- 实施计划：`docs/plans/plan-<feature-name>.md`

不要使用 Superpowers 默认的 `docs/superpowers/specs/` 或
`docs/superpowers/plans/`。

当前已有文件按这个规则命名，例如：

- `docs/specs/feature-reliable-sse-generation.md`
- `docs/plans/plan-reliable-sse-generation.md`

## 何时写 Spec

适合先写 spec 的情况：

- 新功能或跨模块改造
- 用户体验、后端接口、数据模型会一起变化
- 需求还需要明确边界

小修复、明确 bug、文案调整通常不需要新 spec。

## Spec 必须包含

保持精简，但至少说明：

1. 背景与问题
2. 目标
3. 非目标
4. 功能需求
5. 验收标准
6. UX/UI 行为，不涉及前端时写“不涉及”
7. 数据模型或接口变化，没有变化时写“无”
8. 测试策略
9. 风险与待确认问题

Spec 阶段只写需求、边界、设计和验收标准，不写完整实现代码。

## 何时写 Plan

用户确认 spec 后，再写对应 plan。plan 要能被后续实现者直接执行：

- 标明对应 feature 文档
- 拆分后端、前端、测试、迁移步骤
- 使用 checkbox 任务列表
- 明确涉及文件和接口
- 明确验证命令和验收标准

## 实现规则

实现阶段遵循 TDD：

1. 先写能复现问题或证明需求的失败测试
2. 再写最小实现让测试通过
3. 最后做必要重构

对于 bug，先使用 `superpowers:systematic-debugging` 找根因，不要直接猜修复。

对于前端 UI 改动，遵循项目既有组件、状态流和布局约束；必要时结合
`frontend-design` 处理交互与视觉一致性。

完成前必须重新验证。至少运行与改动相关的测试或类型检查，不能只凭代码阅读宣布完成。

## 推荐流程

```text
需求不清楚
  → 澄清需求或写 spec
  → 用户确认 spec
  → 写 plan
  → TDD 实现
  → 验证
  → 总结

明确 bug
  → systematic-debugging
  → 最小复现/失败测试
  → 修复
  → 验证
  → 总结
```

## Specs 必须包含的章节

每个 specs 文件必须包含以下章节，并使用中文标题：
1. `背景（Background）`
   - 说明为什么要做这个功能
   - 当前存在什么问题
   - 这个功能解决什么真实场景
2. `目标（Goal）`
   - 用 1-3 句话说明本次功能要达成什么结果
3. `非目标（Non-Goals）`
   - 明确这次不做什么
   - 防止实现阶段扩大范围
4. `用户故事（User Stories）`
   - 从用户视角描述功能
   - 推荐使用 “作为...我希望...以便...” 的格式
5. `功能需求（Requirements）`
   - 列出明确的功能行为
   - 每条需求必须可以被实现和验证
6. `验收标准（Acceptance Criteria）`
   - 列出可验收的行为结果
   - 每条验收标准都应该能转化为测试用例
   - 必须覆盖正常路径、错误路径、边界情况
7. `边界情况（Edge Cases）`
   - 列出异常输入、失败场景、极端情况
8. `交互与界面行为（UX / UI Behavior）`
   - 如果涉及前端，说明页面行为、loading、empty state、error state、交互反馈
   - 如果不涉及前端，写 `不涉及`
9. `数据模型（Data Model）`
   - 说明涉及的数据结构、字段、状态
   - 如果不涉及数据结构变化，写 `无数据模型变更`
10. `接口设计（API / Interface Design）`
    - 说明接口、函数、模块边界或调用方式
    - 如果不涉及 API，写 `无接口变更`
11. `架构说明（Architecture Notes）`
    - 说明关键设计决策
    - 说明与现有系统如何集成
    - 不要写完整实现代码
12. `测试策略（Testing Strategy）`
    - 说明需要哪些测试
    - 必须包括适用的单元测试、集成测试或端到端测试
    - 必须明确哪些验收标准对应哪些测试
13. `风险（Risks）`
    - 说明潜在风险、兼容性问题、复杂点
14. `待确认问题（Open Questions）`
    - 列出仍需用户确认的问题
    - 如果没有问题，写 `无`

## Plans 必须包含的章节
每个 plan 文件必须包含以下章节：

1. `功能概述（Overview）`
   - 说明这个计划实现哪个功能
   - 引用对应 specs 文件路径

2. `目标（Goal）`
   - 用 1-3 句话说明本计划最终要交付什么

3. `范围（Scope）`
   - 说明本计划会修改什么
   - 明确不会修改什么

4. `技术栈（Tech Stack）`
   - 列出相关语言、框架、测试工具、构建工具

5. `涉及文件（Files）`
   - 列出需要创建、修改、测试的文件
   - 每个文件要说明职责

6. `任务拆分（Tasks）`
   - 每个任务必须足够小
   - 每个任务必须可以独立验证
   - 每个任务必须包含具体文件路径

7. `TDD 执行步骤（TDD Steps）`
   - 每个涉及行为变更的任务必须包含：
     - 写失败测试
     - 运行测试并确认失败
     - 写最小实现
     - 运行测试并确认通过
     - 重构
     - 再次运行测试
   - 不允许先写实现再补测试

8. `验证命令（Verification Commands）`
   - 列出每一步要运行的测试、类型检查、lint 或构建命令
   - 每个命令要写明预期结果

9. `提交计划（Commit Plan）`
   - 说明建议的提交粒度
   - 每个任务完成后是否提交
   - 提交信息必须简洁、英文、符合项目习惯

10. `风险与回滚（Risks and Rollback）`
    - 说明可能影响的模块
    - 说明失败后如何回滚或隔离问题

11. `完成标准（Definition of Done）`
    - 所有验收标准都有对应实现
    - 所有相关测试通过
    - 无新增 lint/type/build 错误
    - 文档已同步
    - 用户确认完成

### 每个任务的固定结构

每个任务必须使用以下结构：

```md
### Task N: 任务名称

**目标：**
说明这个任务完成什么。

**涉及文件：**
- Create: `path/to/file`
- Modify: `path/to/file`
- Test: `path/to/test`

**步骤：**

- [ ] Step 1: 写失败测试
  - 文件：`tests/...`
  - 测试内容：...
  - 运行命令：`...`
  - 预期结果：测试失败，失败原因是目标功能尚未实现

- [ ] Step 2: 写最小实现
  - 文件：`src/...`
  - 实现内容：...
  - 不允许加入 specs 外的功能

- [ ] Step 3: 运行测试
  - 命令：`...`
  - 预期结果：测试通过

- [ ] Step 4: 重构
  - 只允许在测试通过后进行
  - 不改变外部行为

- [ ] Step 5: 再次验证
  - 命令：`...`
  - 预期结果：全部通过

- [ ] Step 6: 提交
  - 提交信息：`feat: ...`

## 写作规则

- specs 阶段只能写需求、设计、边界和验收标准，不允许直接写实现代码。
- 不允许出现 `TBD`、`TODO`、`后续补充` 这类占位内容。
- 不允许写模糊描述，例如 “优化体验”、“处理异常”、“提升性能”，必须说明具体行为。
- 每条验收标准必须是可验证的。
- 如果需求不清楚，必须先向用户提问，不要自行假设，不自行扩大范围。
- 在 specs 文件完成后，必须等待用户确认，不能直接进入实现。
- 用户确认 specs 后，才能使用 `superpowers:writing-plans` 创建 plan。
- 实现阶段必须使用 TDD：先写失败测试，再写最小实现，再重构。
- plan 文件中必须包含所对应的 specs 文件
- 每个步骤都必须有具体动作、文件路径和验证方式。
- plan 阶段不允许包含 specs 外的新功能。
- 如果 plan 发现 specs 有歧义，必须回到 specs 阶段，不要自行补设定。
- plan 只描述如何实现，不直接修改代码。
- plan 完成后必须等待用户确认，不能直接进入实现。
